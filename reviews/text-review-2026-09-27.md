1. **SM 一节缺少“为什么单独分工”的解释。**

   位置：[notes/index.md](../notes/index.md) 第 118、122 行。正文直接进入“通信 block 太少或太多”的权衡，接着介绍自适应控制器。读者能看懂如何分配，却仍不知道为什么要把通信交给独立角色，以及这种选择何时值得采用。这也是目前关于 motivation 最明显的解释缺口。

   建议在资源图前补两段，分别说明论文的设计理由和由此得到的适用条件：

   > mKernel 将计算和通信交给不同的 thread block。计算 block 执行 GEMM 时，通信 block 可以检查数据就绪状态、搬运节点内数据并推进网络请求。调整两类 block 的数量，就能改变资源分配，同时保留计算 block 原有的 warp 布局。
   >
   > 从资源取舍看，这种分工适合通信需要持续推进、同时还有独立计算可做的场景。它能否缩短总耗时，取决于减少的等待能否抵消计算资源减少和同步带来的成本。当 NIC 已经饱和时，继续增加通信资源可能只会拖慢 GEMM。

   前一段依据[论文 §3.2](https://arxiv.org/html/2609.13585v1#S3.SS2)，后一段是结合[论文 §2.2](https://arxiv.org/html/2609.13585v1#S2.SS2)的资源模型作出的设计判断。这里通过 block 角色描述分工，避免让“分 SM”被读成代码固定绑定了物理 SM 编号。现有单节点 8×H100 的自适应实验限定应继续紧邻相关结论。

4. **“就绪”与“何时提交或执行”有两处混淆。**

   位置：[notes/index.md](../notes/index.md) 第 16、104 行。“所需数据完成后立即推进”容易被理解成就绪后没有调度、凑 chunk 或提交等待；这比后文实际描述的机制更强。建议改为：

   > mKernel 在 kernel 内发布局部数据的就绪状态，使下游无需等待整个 producer kernel 结束，即可处理已满足依赖的工作。

   表格中的“命令已就绪或收集窗口到期”则把前置条件与提交时机写成了二选一。根据[论文 §3.3](https://arxiv.org/html/2609.13585v1#S3.SS3)，到期释放的是已收集的就绪命令。建议将列名改为“就绪／提交条件”，batch 单元格改成：

   > 仅收集同连接的就绪命令；可提交不足 8 条的批次，例如在有界收集窗口结束时提交。

5. **Ring Attention 的机制与短序列实测趋势需要分开叙述。**

   位置：[notes/kernels.md](../notes/kernels.md) 第 81 行。“计算覆盖 KV 交换延迟”后立刻接“短序列每步计算较少……相对收益通常更大”，读者容易追问：计算更少，重叠窗口也更短，为什么相对收益反而更大？原句与[论文 §5.4](https://arxiv.org/html/2609.13585v1#S5.SS4)的趋势描述一致，问题在于它没有交代相对收益所比较的基线，也没有区分机制说明与实验观察。

   建议改为：

   > 同一份 KV 可同时供当前 attention 计算和向下一 GPU 的传输使用，从而让两项工作重叠；下一轮仍需等待所需 KV 到达。论文在所测配置中观察到，短序列相对基线的收益通常更大，并将这一趋势联系到通信开销更难被计算摊薄。该趋势描述的是相对基线的总耗时改善，不能据此推断短序列有更长的计算重叠窗口。

   不宜在没有额外证据时，将这组趋势具体归因于 kernel launch、某种同步或某项固定成本的减少。
