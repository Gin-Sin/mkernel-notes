# 性能结果、比较口径与适用边界

论文对多节点融合的直接证据是**算子级 benchmark**。GEMM + AllReduce 最高 1.72×、Ring Attention 最高 1.88×，均针对论文选定的未融合基线与输入范围。它们不能直接当成整模型训练或 serving 的端到端加速。[论文 §5](https://arxiv.org/html/2609.13585v1#S5)

本页数字均来自论文 v1；未在本笔记环境复跑 GPU 实验。交互示例和字节量推导不计入实测结果。

## 1. 实验条件与统计口径

| 项目 | ConnectX-7 测试床 | AWS EFA 测试床 |
|---|---|---|
| GPU | 2 节点 × 8 H200 | 2 节点 × 8 H200 |
| 节点内 | NVLink / NVSwitch | NVLink / NVSwitch |
| 每节点 NIC | 8 × 400 Gb/s CX7 | 16 × 200 Gb/s EFA |
| 每 GPU 跨节点带宽 | 400 Gb/s，即 50 GB/s | 400 Gb/s，即 50 GB/s |
| 网络 | InfiniBand RC | EFA SRD |

编译目标为 Hopper `sm_90a`，CUDA 12.9，每 GPU 一个进程。测试先 warm-up，再连续 launch、末尾同步，用**最慢 rank 的执行时间**衡量算子完成时间。图 5、图 6 显示 TFLOPS/GPU，越高越好。[论文 §5.1，表 4](https://arxiv.org/html/2609.13585v1#S5.SS1)

“两个 16-GPU 集群”表示两套独立测试床，各有 16 GPU；不能理解为一次 32-GPU 的联合实验。SM 自适应部分另用单节点 8×H100，见本页第 4 节。

## 2. 相对未融合基线的结果

| 算子 | AWS EFA | ConnectX-7 | 比较范围与限定 |

| Ring Attention | 最高 **1.78×** | 最高 **1.88×** | 相对未融合 attention + 通信基线 |

数字出处：[论文 §5.2](https://arxiv.org/html/2609.13585v1#S5.SS2)、[§5.3](https://arxiv.org/html/2609.13585v1#S5.SS3)、[§5.4](https://arxiv.org/html/2609.13585v1#S5.SS4)。最高倍率通常对应特定 shape；不能把不同算子的峰值视为同一个模型配置的共同收益。

**倍率换算。** 相同工作量下，加速比 $s=T_{\mathrm{baseline}}/T_{\mathrm{mKernel}}$。1.72× 对应耗时约为基线的 58.1%，即降低约 41.9%；1.88× 对应耗时约为 53.2%，即降低约 46.8%。这是由倍率计算的换算，不是新的测量结果。

### MoE 两个必须保留的限定

**未融合基线较弱。** 论文的 EFA all-to-all + GEMM 基线假定 uniform routing，且没有 grouped expert GEMM。因此，3.1–4.5× 同时包含专家计算组织和通信重叠收益，缺少消融时无法把整个倍率分配给某一项设计。

**DeepEP 图柱跨测试床。** 论文所用 DeepEP + DeepGEMM 实现采用 IBGDA，未支持 EFA。EFA 图中的对应柱来自 ConnectX-7，是跨测试床参考。这一结果无法单独证明在相同 EFA 环境、相同后端下 mKernel 比 DeepEP 更快。这里描述的是论文使用的版本，不是对 DeepEP 所有后续版本的断言。[论文 §5.1、§5.3，图 5 图注](https://arxiv.org/html/2609.13585v1#S5.SS3)

## 4. 自适应 SM：接近最佳固定分配的成本

图 3 使用**单节点 8×H100**，覆盖 GEMM + AllReduce、GEMM + ReduceScatter、MoE Dispatch + GEMM、Ring Attention，共 21 个配置。纵轴定义为某配置延迟除以该 shape 的最佳固定分配延迟，虚线为 1，越低越好。[论文图 3](https://arxiv.org/html/2609.13585v1#S3.F3)

论文 §5.5 报告自适应相对最佳固定分配的几何平均比值为 **1.18×**。结合图 3 的归一化延迟定义，应理解为平均延迟比约 1.18，即约 18% 的相对延迟开销，**不能表述为 18% 加速**。这里是对图轴和正文的联合解读；正文该句本身没有重新写出比值分子与分母。[论文 §5.5](https://arxiv.org/html/2609.13585v1#S5.SS5)

它的收益在于：无需逐 shape 搜索，也能避开很差的固定分配，并在 kernel 内根据剩余工作调整角色。最佳固定分配通过离线扫描才知道，二者比较包含了调参成本与运行性能的取舍。

| 观察 | 可以支持什么 | 不能推出什么 |
|---|---|---|
| 最佳通信 SM 从 2 到 64 变化 | 一个固定比例难以适配全部 workload | 所有 GPU 都应在 2–64 中选择 |
| 最差 AllReduce 分配约慢 25× | 极端资源错配可造成巨大等待 | mKernel 比 NCCL 快 25× |
| 21 个配置几何平均延迟比约 1.18 | 自适应可接近扫描得到的最佳固定分配 | 自适应普遍优于最佳静态配置 |
| 计算末期目标转向通信 | 剩余工作能驱动阶段内调整 | 已证明跨多节点控制的收益和稳定性 |

## 5. 哪些贡献有直接对照

| 主张 | 论文证据 | 证据边界 |
|---|---|---|
| 多节点融合算子更快 | 两套 2×8 H200 测试床上的算子对比 | 未覆盖任意规模、拓扑与 shape |
| proxy 路径可接近 IBGDA | 相同 kernel 在 CX7 上切换后端，图 4 | 未证明所有小消息与 CPU 负载场景都等效 |
| SM 分配影响性能 | 单节点静态扫描，图 3 | 配置扫描不等于跨系统基线比较 |
| 自适应目标能随剩余工作变化 | 图 7 的 kernel 内轨迹 | 动态轨迹本身不能量化端到端收益 |
| 分层通信和粒度选择有用 | 设计分析与整体性能结果 | 不能从整体倍率反推出每项机制的独立贡献 |

单节点、tile 级融合、SM 分工和 host proxy 都有前序工作。论文的贡献应放在**跨节点三阶段协同、粒度衔接、跨传输语义的实现与五类算子验证**上，而不能声称它首次提出其中每一个基本机制。论文 §6 明确讨论 FLUX、ParallelKittens、Triton-distributed、Mercury、UEP、NVSHMEM 等工作。[论文 §6](https://arxiv.org/html/2609.13585v1#S6)

## 6. 向完整系统外推的条件

如果被优化算子原占总时间的比例为 $f$，算子加速 $s$ 倍，其余部分不变，则 Amdahl 近似为

$$
S_{\mathrm{end-to-end}}=\frac{1}{(1-f)+f/s}.
$$

例如，**假设**一个算子占总时间 30%，加速 1.72×，则端到端只有约 1.14×。此示例用于解释范围，不是论文的模型实测。

对实际训练或 serving，还要重新检查：动态 batch 与序列长度、MoE routing 不均衡、与其他 kernel 的并发、CPU proxy 的可用核与 NUMA 位置、网络拓扑、缓冲区与 epoch 生命周期，以及整模型最慢 rank 的变化。论文为这些工程取舍提供了可复用设计，但当前结果并未逐一验证这些场景。
